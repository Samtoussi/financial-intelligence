# M003: Two-Filing Generalization & Reliability

M003 supports exactly two observed Microsoft Q1 10-Q layouts through explicit
profiles. It adds no services, dependencies, UI, or general filing-discovery
framework. M002 remains the default. The separate M001 fixture, validator, and
tests are unchanged.

| Profile | Accession | Period | Segments | Metric pairs |
|---|---|---|---:|---:|
| `msft_fy2027_q1` (default) | `0001193125-26-436133` | July-September 2026 vs 2025 | 2 | 6 |
| `msft_fy2026_q1` | `0001193125-25-256321` | July-September 2025 vs 2024 | 3 | 7 |

Profiles in `src/analytics/report_profiles.py` contain pinned source identity,
periods, metric labels/units/basis, segment labels, bounded evidence anchors,
and interpretation topics. They contain no oracle values. The generator receives
only report metadata, requested metric definitions, topics, and source evidence.
Oracle fixtures are loaded and archived after generation, never sent to the model.
New runs also archive the profile; offline re-evaluation checks its identity against
the selected configuration. Legacy runs without a profile artifact infer the profile
from their pinned accession.

## Behavior and checks

The existing Part I TOC extractor works unchanged for both cached sources. Profile
anchors preserve M002 evidence spans/IDs exactly. FY2026 Q1 uses its observed
segment-table ending and Note 16 reporting-basis paragraph. Missing boundaries,
wrong source identity, or reversed/missing/extra period columns fail closed.
Offsets, section/text/source hashes, and overlapping chunk IDs are retained.
Offline re-evaluation rebuilds evidence from saved section spans and provenance.

Structured output derives metric IDs/counts from the profile: four consolidated
metrics plus every declared segment revenue. The Responses API model, one-call
pattern, timeout, no-retry configuration, and deterministic Markdown rendering
remain unchanged. Default M002 instructions, topics, and schema remain the same;
the second profile uses prompt version `m003-v1` in legacy mode. The opt-in
`m003-v2` mode uses `m003-v2-contract-v1`, described below.

Report-level ground-truth validation is separate from the unchanged M001 validator.
Expected counts, units, periods, segment reconciliation, source row labels and
columns derive from the selected profile. Evaluation retains exact Decimal checks,
ROUND_HALF_UP one-decimal YoY, labeled row support, quoted row/segment labels,
source identity, hash checks, citation integrity, and quote membership. Table
support requires exactly the declared current/prior years in header order.
Pending, failed, unattributed, or unsupported manual reviews cannot yield a pass.

## Reproduce

Use the existing `.venv`; `.env` is loaded only by generation, with environment
values taking precedence. No dependencies were added.

```powershell
# Full offline suite, including both cached sources when available.
.venv/Scripts/python.exe -m pytest tests -q -p no:cacheprovider --basetemp=data/test_tmp/m003-verification

# Read-only regression against approved M002 output (does not rewrite its history).
.venv/Scripts/python.exe -m pytest tests/test_report_profiles.py::test_approved_m002_evidence_and_result_are_reproduced_read_only -q -p no:cacheprovider

# One live generation using the already cached second accession (no SEC call).
.venv/Scripts/python.exe evals/run_report.py --profile msft_fy2026_q1

# Default remains M002. Explicit selection is also supported.
.venv/Scripts/python.exe evals/run_report.py --profile msft_fy2027_q1

# Offline evaluation of a NEW run. This replaces that run's evaluation/run status.
.venv/Scripts/python.exe evals/run_report.py --evaluate-run evals/reports/m003/<run_id>
# After human review: copy review_template.json to review.json and record decisions.
.venv/Scripts/python.exe evals/run_report.py --evaluate-run evals/reports/m003/<run_id> --reviews evals/reports/m003/<run_id>/review.json
```

`--snapshot` pins an explicit cached file; `--download` uses SEC discovery and
fetch for the selected accession. Both are incompatible with `--evaluate-run`.
A conflicting explicit profile during re-evaluation is rejected. New second-profile
runs live under `evals/reports/m003/`; M002 retains its original destination.
All run artifacts remain Git-ignored. Exit codes: 0 all checks and reviews pass;
2 automatic checks pass but manual reviews pending/failed; 1 automatic failure
or incomplete execution.

## Limits

Two observed Q1 layouts do not establish support for other issuers, Q2/Q3
quarter-versus-YTD columns, arbitrary segment structures, negative/zero oracle
values, or changed HTML. This milestone preserves the existing positive-value
and income-ordering fixture constraints for these two sources. Hashes and quote
membership do not establish source authenticity or semantic entailment. A live
sample is feasibility evidence, not an estimate of reliability.

## Opt-in reliability mode: m003-v2

The default remains the existing M002 generation path, instructions, and output
schema. Select the new version explicitly:

```powershell
.venv/Scripts/python.exe evals/run_report.py --profile msft_fy2026_q1 --generation-mode m003-v2
```

`src/ai/report_assembly.py` extracts unique labeled current/prior rows from the
validated bounded evidence packets. It rejects unsupported cells, missing or
ambiguous rows, wrong column years, mismatched source identities, and duplicate
packets. Segment rows are bounded by the next declared segment or Total heading;
the EPS row is bounded before weighted-average shares. Positive prior values are
required. Decimal arithmetic uses precision 60 and one final `ROUND_HALF_UP`
quantization to one decimal. No evaluation fixture or evaluator is imported.

Each numeric input retains its original token, period column, metric, evidence
ID, source hash/accession, and supporting span ID. Span IDs bind source and
section hashes, character offsets, and the supported metric or interpretation
topic. Quotations are unmodified UTF-8 slices of the saved extracted source text,
including empty table delimiters; they are not quotations of raw HTML markup.
Python assembles all financial fields and numeric citations. The model returns
only interpretation notes and span IDs. Assembly rejects unknown IDs, references
to a different claim/topic, and altered registries. Semantic entailment of narrative
assertions still requires human review; topic binding does not prove it.

New-mode runs archive `assembly_inputs.json`, `raw_response.json` (the API response),
`raw_llm_text.json` (the exact response text as a JSON string), and `raw_llm.json`
separately from assembled `generated.json` and `summary.md`. Raw output is saved
before parsing/assembly, including incomplete responses when available.
Re-evaluation rebuilds the registry and report from saved source evidence and raw
notes before passing the report through the unchanged independent evaluator.
Original M002 artifacts and the failed M003 baseline are never rewritten by this
validation. New-mode runs for either profile are stored under `evals/reports/m003`.

## M003-v2 model-facing contract correction

The controlled retry `20261030T210941Z_60e7f993` received a completed API response,
but strict assembly rejected four citations across three numeric span IDs. The
segment-comparability note cited all three segment revenue spans; the Azure/Cloud
margin note also cited the Intelligent Cloud revenue span. Each numeric quotation
was genuine but bound to a metric, not the note topic. The appropriately bound
qualitative spans were already cited as well. Assembly stopped at the first invalid
reference; the other three would fail the same check. No report or evaluation was
produced, and the response remains rejected without alteration.

The previous prompt requested supporting IDs without explicitly requiring a topic
match. Its schema accepted arbitrary strings for `span_ids`, while the application
required `span.claim_id == note.id`. That model-facing mismatch is now corrected
within the opt-in `m003-v2` mode. New runs identify the revised prompt as
`m003-v2-contract-v1`; previous run artifacts retain their original versions.

After source evidence validation, topic-specific `allowed_span_ids` lists are
computed directly from the reconstructed registry's claim bindings. No observed
hashes are hardcoded. Every interpretation topic in the request contains its ID,
question, and explicit eligible-ID list. Instructions require selection only from
that list and explain that numeric metric spans are context, not note citations,
unless explicitly bound to that topic. This correction introduces no new bindings.

The structured output keeps `notes` as an array of `{id, text, span_ids}` objects.
Its item schema uses nested `anyOf` alternatives: each branch permits exactly one
topic ID and only that topic's span-ID enum. The root remains an object. All object
fields are required and `additionalProperties` is false. It introduces no `if/then`,
`oneOf`, tuple schemas, or custom schema keywords. Missing eligible-topic spans fail
before a request. Duplicate topic detection remains an application responsibility;
three array elements alone cannot establish topic uniqueness.

The actual evidence-specific schema is saved as `output_schema.json` after registry
construction, before the model call, together with `allowed_span_ids.json`. The same
schema object is supplied to the Responses API. Instructions, raw-response storage,
source identity checks, registry comparison, exact quote resolution, numeric
calculations, assembler rejection rules, independent evaluator, and mandatory human
review otherwise retain their contracts. M002's default prompt/schema are unchanged.

Offline schema checks use the already installed JSON Schema validator and the
installed OpenAI SDK's strict-schema normalization. Both profiles' schemas are valid,
normalization leaves them unchanged, and wrong-topic, numeric, and unknown IDs are
rejected. At this offline checkpoint, server acceptance had not yet been tested.
The final live validation below subsequently confirmed acceptance. No dependencies
were added. The original failed response is rejected by both the corrected schema and
the unchanged assembler; no invalid references are removed or silently ignored.
